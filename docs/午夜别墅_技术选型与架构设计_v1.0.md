# 《午夜别墅》技术选型与架构设计文档

**版本：** V1.0\
**依据：** PRD V1.2、游戏设计文档 V1.0\
**目标：** 以较低开发和运行成本交付浏览器端单人 3D 悬疑探索游戏。

------------------------------------------------------------------------

## 1. 技术目标与约束

### 1.1 技术目标

-   在桌面浏览器运行 3D 游戏。
-   支持第一人称移动、场景碰撞和物品交互。
-   支持 NPC 对话、线索、任务、谜题和剧情分支。
-   支持本地存档。
-   便于个人开发和 AI Coding 协作。
-   为后续 AI NPC 接入预留边界，但不让 MVP 依赖在线模型服务。

### 1.2 当前约束

-   个人开发，开发周期约一个月。
-   开发设备为 MacBook Air M4、16GB 内存。
-   本地剩余存储空间有限，需控制源资产和构建产物。
-   3D 生成积分有限，资产策略以复用和模块化为主。
-   目标是 Web 浏览器交付，优先桌面端。

## 2. 技术选型总览

  ---------------------------------------------------------------------------------------------
  层级              选型              职责                       说明
  ----------------- ----------------- -------------------------- ------------------------------
  3D 引擎           PlayCanvas Engine 场景、渲染、摄像机、动画   核心运行时

  编辑器            PlayCanvas        场景编辑和资源组织         根据工作流决定是否使用
                    Editor（可选）                               

  UI                React             首页、菜单、对话、设置     不负责 3D 场景渲染

  构建              Vite              开发服务器和构建           统一前端工程

  语言              TypeScript        UI 与游戏逻辑              开启严格类型检查

  3D 内容           Blender           模型调整、碰撞体、导出     输出 GLB / glTF

  资源格式          GLB / glTF        模型、材质、动画           优先统一格式

  本地存档          IndexedDB         进度、设置、状态           首期无需账号

  部署              静态 Web 托管     发布前端构建产物           可选择支持大文件和缓存的托管
  ---------------------------------------------------------------------------------------------

### 2.1 PlayCanvas 的职责

PlayCanvas 负责： - WebGL / WebGPU
场景渲染能力（具体后端以目标浏览器和当前引擎版本支持情况为准）； -
摄像机与第一人称控制； - 3D 模型、材质和动画加载； -
射线检测与空间交互； - 场景节点和实体管理； - 灯光、阴影和后处理； -
音频空间化及场景音效。

### 2.2 React 的职责

React 负责： - 首页与主菜单； - 对话框和玩家选项； - 线索查看面板； -
任务提示； - 暂停菜单； - 设置界面； - 存档状态提示。

React 不应每帧驱动 3D 场景更新。高频游戏循环由 PlayCanvas 侧处理。

## 5. 核心模块设计

### 5.1 GameBootstrap

负责： - 初始化 PlayCanvas Application； - 获取并初始化 Canvas； -
加载首个场景； - 注册输入、事件和系统； - 与 React UI 建立通信； -
处理游戏销毁和资源释放。

### 5.2 PlayerController

负责： - WASD 移动； - 鼠标视角； - Pointer Lock； -
移动速度和灵敏度； - 碰撞与地面检测； - 暂停时冻结输入。

建议先实现稳定的胶囊体控制与碰撞，再考虑奔跑和其他移动能力。

### 5.3 InteractionSystem

采用摄像机中心射线检测： 1. 从摄像机中心发射射线； 2. 检查交互距离； 3.
判断目标是否实现可交互接口； 4. 显示对应提示； 5.
用户按下交互键时调用目标交互逻辑。

建议定义统一接口：

``` typescript
interface Interactable {
  id: string;
  getPrompt(context: InteractionContext): string | null;
  canInteract(context: InteractionContext): boolean;
  interact(context: InteractionContext): void;
}
```

### 5.4 NPCSystem 与 DialogueSystem

NPCSystem 管理 NPC 实例、状态、动画和交互入口。

DialogueSystem 管理： - 对话节点读取； - 条件判断； - 玩家选项； -
节点跳转； - 状态效果； - 对话结束。

对话内容存放在独立数据文件中，不硬编码在 React 组件或 NPC 脚本里。

### 5.5 StoryStateMachine

统一维护剧情状态和事件。

建议提供： - `getFlag(key)`：读取剧情标记； -
`setFlag(key, value)`：更新标记； - `dispatch(event)`：分发剧情事件； -
`evaluateConditions(conditions)`：检查触发条件； -
`resolveEnding()`：根据状态判定结局。

重要状态更新应通过统一入口完成，避免不同系统直接修改彼此内部对象。

### 5.6 SaveManager

负责： - 新建存档； - 加载存档； - 自动保存； -
手动保存（如设计需要）； - 存档版本校验； - 数据迁移； - 存档损坏处理。

## 6. 数据模型建议

### 6.1 SaveData

``` typescript
interface SaveData {
  schemaVersion: number;
  updatedAt: number;
  currentSceneId: string;
  player: {
    position: [number, number, number];
    rotation: [number, number, number];
  };
  storyFlags: Record<string, boolean | number | string>;
  discoveredClueIds: string[];
  completedPuzzleIds: string[];
  completedQuestIds: string[];
  npcStates: Record<string, NPCState>;
  choices: Record<string, string>;
}
```

### 6.2 NPCState

``` typescript
interface NPCState {
  npcId: string;
  mood: string;
  relationship: number;
  currentDialogueNode: string | null;
  unlockedDialogueIds: string[];
  flags: Record<string, boolean | number | string>;
}
```

### 6.3 内容数据与运行状态分离

静态内容定义： - NPC 角色卡； - 对话树； - 线索内容； - 谜题配置； -
任务定义； - 剧情事件定义。

运行时状态： - 玩家发现了什么； - NPC 当前态度； - 哪些谜题已完成； -
哪些剧情节点已触发； - 玩家作出过哪些选择。

静态内容可随构建发布，运行时状态写入 IndexedDB。

## 7. 本地存储设计

首期使用 IndexedDB，而非把完整游戏状态仅存入 localStorage。

建议对象仓库： - `saves`：存档主体； - `settings`：用户设置； -
`metadata`：存档列表和版本信息。

存档策略： - 关键线索发现后保存； - 谜题完成后保存； -
关键剧情选择后保存； - 场景切换后保存； - 设置修改后保存。

避免每帧写入数据库。位置等高频状态可以在定时或关键节点保存。

## 8. 资源加载策略

### 8.1 资源分组

-   `core`：启动必需资源；
-   `common`：常用材质、交互 UI 和基础音效；
-   `scene_*`：各区域场景资源；
-   `npc_*`：NPC 模型与动画；
-   `story_*`：特定剧情资产。

### 8.2 加载原则

-   首屏只加载进入游戏所需资源。
-   按区域加载场景内容。
-   可复用模型和材质尽量共享。
-   离开区域后按需释放不再使用的资源。
-   对大贴图和模型进行压缩。
-   在真实浏览器中测量加载时间和显存占用。

## 9. 渲染与性能策略

优先级从高到低：

1.  保证玩家移动、交互和 UI 响应稳定；
2.  保证主要场景可见性；
3.  控制动态灯光与阴影；
4.  对静态环境使用烘焙光照；
5.  控制模型面数和材质数量；
6.  使用实例化处理重复物体；
7.  按距离使用 LOD；
8.  逐步增加后处理效果。

不要一开始同时启用大量高成本效果。每增加一种效果，都应在目标设备上测量收益和成本。

## 10. 音频架构

AudioManager 统一管理： - 环境循环音； - 区域音效； - 玩家脚步； -
物品交互； - NPC 对话； - 剧情事件音效。

支持主音量、音乐音量和音效音量。浏览器自动播放策略可能限制声音启动，应在用户主动开始游戏后初始化或恢复音频上下文。

## 11. AI NPC 扩展接口

AI NPC 不属于 MVP 必需功能。后续如需自然语言交互，建议增加独立服务层：

``` text
Browser Game
   |
   | NPC conversation request
   v
Go API / AI Gateway
   |
   +-- Context Builder
   +-- Character Profile
   +-- Knowledge Boundary
   +-- Dialogue Model Provider
   +-- Output Validation
   |
   v
Structured NPC Response
   |
   v
Game Dialogue System
```

约束： - 浏览器不保存模型 API 密钥； - 请求只传递必要剧情上下文； - NPC
知识边界由游戏内容控制； - 模型输出应结构化并校验； -
模型不能直接修改结局和关键任务状态； -
网络失败时回退到预设对话或提示玩家稍后重试。

## 12. 安全与可靠性

即使是单机浏览器游戏，也应考虑： - 对存档数据做 schema 校验； -
对外部资源路径进行白名单管理； - 不在前端代码中放置私密 API 密钥； -
处理 IndexedDB 不可用或空间不足； - 对存档版本升级提供迁移逻辑； -
资源加载失败时显示可理解的错误提示。

## 13. 开发阶段与技术验收

### 第 1 周：引擎与场景基础

-   React + Vite + TypeScript 工程；
-   PlayCanvas 初始化；
-   第一人称控制；
-   碰撞与射线检测；
-   灰盒别墅场景。

验收：能够在浏览器中稳定进入场景并移动、交互。

### 第 2 周：内容系统

-   NPC 实例；
-   对话树；
-   线索数据；
-   交互 UI；
-   基础事件总线。

验收：NPC 对话选择可以更新剧情标记，线索可发现和查看。

### 第 3 周：剧情与存档

-   剧情状态机；
-   谜题与任务；
-   结局判定；
-   IndexedDB 存档。

验收：完整流程可通关，刷新后可恢复进度。

### 第 4 周：性能与发布

-   模型与贴图优化；
-   灯光和音频；
-   浏览器兼容性；
-   存档异常测试；
-   Web 部署。

验收：目标桌面浏览器可完整体验游戏。

  ----------------------------------------------------------------------------------
  风险                    影响                    应对
  ----------------------- ----------------------- ----------------------------------
  PlayCanvas 与 React     中                      统一 GameBootstrap 和销毁流程
  生命周期管理复杂                                

  大场景加载过慢          高                      分区加载和资源压缩

  实时阴影成本高          高                      烘焙优先、动态光源克制

  对话与剧情状态耦合      高                      统一状态机和事件接口

  AI 对话产生错误剧情信息 高                      后续接入时增加知识边界和输出校验
  ----------------------------------------------------------------------------------

## 15. 最终技术结论

当前推荐采用：

-   **PlayCanvas**：3D 游戏运行时；
-   **React + Vite + TypeScript**：UI 和工程基础；
-   **Blender + GLB/glTF**：模型制作与资产管线；
-   **IndexedDB**：本地游戏存档；
-   **静态 Web 托管**：MVP 发布。

首期不需要独立 Go 后端、数据库服务或实时通信服务。只有在后续确实需要 AI
NPC、云存档或其他在线能力时，再引入对应后端。

技术实现应以最短路径交付完整可玩的单人游戏为原则。
