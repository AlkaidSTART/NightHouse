## 1. 产品概述

### 1.1 产品定位

《午夜别墅》是一款单人第一人称写实悬疑探索游戏。玩家将在深夜进入一座充满秘密的别墅，通过探索环境、与 NPC 交流、收集线索、解决谜题以及作出关键选择，逐步揭开别墅背后的真相。

游戏以沉浸式环境和人物互动为核心。玩家的探索行为、已发现线索和关键选择会影响后续对话、剧情推进及最终结局。

### 1.2 核心体验目标

1. **沉浸探索：** 通过第一人称视角、空间布局、灯光和声音营造可信的别墅环境。
2. **人物互动：** NPC 拥有独立身份、性格、背景和对玩家的态度变化。
3. **线索推理：** 玩家从物品、文件、环境细节和 NPC 对话中获得信息。
4. **选择影响：** 玩家作出的关键选择会改变剧情状态，并影响后续内容。
5. **完整闭环：** 玩家能够从开场进入游戏，经历探索与推理，最终抵达明确结局。

### 1.3 产品设计原则

- 优先保证核心探索与剧情体验完整。
- NPC 的行为和对话必须服务于人物塑造及剧情推进。
- 重要剧情信息应有明确来源和触发条件。
- 采用数据驱动的对话、线索和剧情配置，降低后续内容制作成本。
- 控制地图规模、模型数量和渲染复杂度，适配个人开发资源。
- 先保证游戏可玩、流程完整，再逐步提升画面表现和交互丰富度。

## 2. 目标用户与使用场景

### 2.1 目标用户

- 喜欢悬疑、惊悚和剧情探索题材的玩家。
- 喜欢通过观察环境、收集信息和推理推进故事的玩家。
- 对具有记忆和态度变化的 NPC 感兴趣的玩家。
- 希望通过浏览器快速体验独立游戏的玩家。

### 2.2 典型游玩流程

1. 玩家打开游戏首页。
2. 开始新游戏并观看开场内容。
3. 玩家进入别墅，熟悉基本操作。
4. 玩家探索房间，发现可交互物品和 NPC。
5. 玩家与 NPC 对话，获取信息或解锁新线索。
6. 玩家整理线索并解决场景谜题。
7. 玩家触发新的剧情节点和场景变化。
8. 玩家作出关键选择。
9. 游戏根据当前剧情状态进入对应结局。
10. 游戏保存本次进度和结局信息。

## 3. 游戏基础设计

### 3.1 视角与操作

采用第一人称视角（First Person）。

| 输入 | 功能 |
|---|---|
| W / A / S / D | 前后左右移动 |
| 鼠标移动 | 控制视角 |
| E | 与 NPC 或场景物品交互 |
| Shift | 奔跑 |
| 空格 | 跳跃 |
| C / Ctrl | 蹲下（C 切换，Ctrl 按住） |
| ESC | 打开暂停菜单并释放鼠标 |

基础要求：

- 支持浏览器 Pointer Lock 鼠标锁定。
- 玩家移动受到场景碰撞体约束。
- 交互对象具有明确的距离和视线检测条件。
- 靠近可交互对象时显示交互提示。
- 提供灵敏度、音量等基础设置。
- 避免过度镜头晃动，减少长时间游玩时的不适。

### 3.2 核心玩法循环

```text
进入别墅
   ↓
探索场景
   ↓
发现 NPC / 可交互物品
   ↓
对话 / 检查物品 / 收集线索
   ↓
获得新信息或解锁条件
   ↓
解决谜题 / 推进任务
   ↓
触发剧情事件
   ↓
作出关键选择
   ↓
进入对应结局
```

## 4. 场景与关卡设计

### 4.1 当前版本场景范围

当前版本以一座小型别墅作为主要探索空间。场景采用模块化布局，在保证探索路线清晰的前提下逐步替换灰盒与临时资产。

建议区域：

- 别墅入口：建立环境氛围，提供基础操作引导。
- 客厅：主要公共空间，可放置关键环境线索。
- 走廊：连接不同区域，承担空间过渡和氛围营造。
- 书房：放置文件、日记或其他信息型线索。
- 卧室：承载人物背景或私人信息。
- 储物区域：放置物品类线索或谜题要素。
- 核心剧情区域：承载关键事件及剧情揭示。

最终房间数量、开放顺序和空间关系由关卡设计阶段确定。

### 4.2 场景交互对象

可交互对象包括：

- 房门、抽屉、柜子。
- 日记、信件、照片、书籍。
- 钥匙及其他剧情道具。
- 灯具和部分环境装置。
- NPC 及剧情触发点。

交互反馈应包含至少一种明确提示，例如界面提示、物体状态变化、音效或对话反馈。

### 4.3 环境叙事

场景不仅作为移动空间，也承担叙事功能。可通过家具摆放、物品状态、照片、文字、声音和灯光暗示人物关系及过往事件。

## 5. NPC 系统

NPC 是游戏核心互动对象。当前版本优先塑造少量具有明确剧情作用的角色，并通过后续迭代逐步提高表演与互动完成度。

### 5.1 NPC 基础设定

每个 NPC 至少包含：

- 唯一 ID。
- 姓名及身份。
- 外观与基础动画。
- 人物背景。
- 性格特征。
- 当前情绪或态度。
- 所属剧情节点。
- 对话内容与解锁条件。
- 与玩家相关的状态标记。

### 5.2 NPC 交互流程

1. 玩家进入 NPC 的交互范围。
2. 游戏显示交互提示。
3. 玩家按下交互键。
4. 打开对话界面。
5. 展示 NPC 当前可用台词。
6. 玩家选择回应或提问。
7. 系统检查选择条件并更新剧情状态。
8. NPC 根据更新后的状态回应。
9. 对话结束后，玩家继续探索。

### 5.3 NPC 状态模型

建议使用 TypeScript 定义 NPC 状态：

```typescript
interface NPCState {
  id: string;
  mood: string;
  relationship: number;
  dialogueNode: string;
  unlockedDialogues: string[];
  flags: Record<string, boolean>;
}
```

字段说明：

- `id`：NPC 唯一标识。
- `mood`：当前情绪状态。
- `relationship`：与玩家的关系数值或等级。
- `dialogueNode`：当前对话节点。
- `unlockedDialogues`：已解锁的对话节点。
- `flags`：与该 NPC 相关的剧情标记。

NPC 状态必须与剧情状态保持一致，并能够写入存档。

### 5.4 对话系统

当前版本采用预设对话树和条件分支。

示例：

```text
玩家：你一直住在这里吗？

NPC：是的，我已经在这里很多年了。

玩家可以选择：
A. 询问别墅的主人
B. 询问最近发生的事情
C. 结束对话

选择 A：
NPC：这座房子的主人已经很久没有出现了。

选择 B：
NPC：最近晚上，总能听见楼上传来声音。
```

对话节点应支持：

- 前置条件。
- 多个玩家选项。
- 选择后的状态变更。
- 对话节点跳转。
- 线索或任务解锁。
- 对话结束条件。

### 5.5 后续 AI NPC 扩展

后续可评估引入大语言模型，为 NPC 增加自然语言交流能力。该能力不属于当前正式版范围，引入前必须单独立项并确认服务、隐私、成本和剧情一致性。

扩展时必须保留以下约束：

- NPC 固定的人物身份和性格。
- NPC 可知信息范围。
- 当前剧情上下文。
- 玩家已经发现的线索。
- 不可提前透露的剧情信息。
- 关键剧情状态和谜题条件由游戏逻辑控制。

模型生成内容不能直接决定关键剧情结果，也不能绕过游戏内的解锁条件。模型服务应通过后端代理调用，避免在浏览器端暴露密钥。

## 6. 线索、任务与谜题系统

### 6.1 线索系统

线索是连接环境探索、NPC 对话和剧情推进的主要机制。

每条线索包含：

| 字段 | 说明 |
|---|---|
| id | 线索唯一标识 |
| title | 线索名称 |
| description | 线索内容 |
| locationId | 所属场景 |
| discoveryCondition | 发现条件 |
| relatedNpcIds | 关联 NPC |
| storyFlags | 发现后更新的剧情标记 |

线索类型可包括：

- 纸条、信件和日记。
- 照片和文件。
- 录音及环境声音。
- 钥匙和特殊物品。
- 场景中具有叙事意义的摆设。

玩家发现线索后，应能够查看其内容；必要时在后续对话或谜题中引用该线索。

### 6.2 任务与目标

当前版本采用轻量任务系统，不建设复杂任务编辑器。

任务至少包含：

- 任务 ID。
- 任务名称。
- 任务描述。
- 当前目标。
- 完成条件。
- 前置条件。
- 完成后的剧情事件。

任务提示应避免直接泄露全部解谜答案。

### 6.3 谜题系统

谜题应与场景和剧情紧密关联，而不是孤立的小游戏。

当前版本优先制作少量可验证的谜题，例如：

- 根据文件信息寻找密码。
- 根据物品位置恢复某种排列。
- 使用已发现的道具打开特定区域。
- 结合 NPC 对话信息判断正确选项。

谜题完成后，由游戏逻辑更新状态并触发后续事件。

## 7. 剧情与结局系统

### 7.1 剧情状态管理

采用事件驱动的剧情状态机。探索、对话、线索发现和谜题完成均可触发状态变化。

示例：

```text
发现书房日记
      ↓
设置 clue_diary = true
      ↓
解锁 NPC 新对话
      ↓
与 NPC 讨论日记
      ↓
设置 npc_secret_unlocked = true
      ↓
解锁隐藏区域
```

### 7.2 多结局设计

正式版至少包含两个可区分的结局，并允许在条件明确时启用隐藏结局。

结局条件可以综合考虑：

- 已发现的关键线索。
- 已完成的谜题。
- NPC 关系或关键互动结果。
- 玩家作出的关键选择。
- 是否满足特定剧情条件。

具体结局内容、触发条件和剧情文本在剧本设计阶段确定。

### 7.3 剧情数据原则

- 重要剧情状态集中管理。
- 对话和线索内容采用数据驱动配置。
- 事件触发条件应明确、可测试。
- 结局判定由游戏逻辑统一执行。
- 存档应记录影响结局的关键选择。

## 8. UI 与交互需求

### 8.1 游戏首页

包含：

- 产品名称与主视觉。
- 开始新游戏。
- 继续游戏（存在有效存档时显示）。
- 设置。
- 游戏说明或制作信息。

### 8.2 游戏内 HUD

保持克制，避免遮挡场景。

建议包含：

- 中央交互准星或提示。
- 交互对象提示。
- 必要的当前目标提示。
- 线索获取反馈。
- 暂停入口。

### 8.3 对话界面

包含：

- NPC 名称。
- NPC 当前台词。
- 玩家可选回应。
- 继续或结束对话的操作。
- 必要时显示已发现线索的关联信息。

### 8.4 线索查看界面

展示线索名称、正文或图片内容，以及必要的发现时间或关联信息。界面应支持关闭并返回游戏。

### 8.5 暂停与设置

至少支持：

- 继续游戏。
- 重新开始（需二次确认）。
- 鼠标灵敏度。
- 主音量与音效音量。
- 返回首页。

## 9. 技术方案

### 9.1 技术选型

| 层级 | 技术 | 用途 |
|---|---|---|
| 3D 游戏引擎 | PlayCanvas | 场景渲染、摄像机、动画、交互 |
| UI 框架 | React | 首页、菜单、对话及设置界面 |
| 构建工具 | Vite | 开发与构建 |
| 开发语言 | TypeScript | 游戏逻辑和 UI |
| 建模与调整 | Blender | 模型检查、碰撞体和资源优化 |
| 资源格式 | GLB / glTF | 3D 模型及动画 |
| 本地存储 | IndexedDB | 游戏进度和设置 |
| 部署 | 静态 Web 托管 | 发布浏览器版本 |

### 9.2 前端模块划分

```text
Browser
├── React
│   ├── Home
│   ├── MainMenu
│   ├── DialogueUI
│   ├── ClueViewer
│   ├── QuestUI
│   ├── PauseMenu
│   └── Settings
│
└── PlayCanvas
    ├── SceneManager
    ├── PlayerController
    ├── InteractionSystem
    ├── NPCSystem
    ├── DialogueSystem
    ├── ClueSystem
    ├── QuestSystem
    ├── StoryStateMachine
    ├── AudioManager
    └── SaveManager
             └── IndexedDB
```

### 9.3 模块职责

- `SceneManager`：场景加载、切换和资源管理。
- `PlayerController`：第一人称移动与视角控制。
- `InteractionSystem`：射线检测、交互距离和交互分发。
- `NPCSystem`：NPC 实例、状态和基础行为。
- `DialogueSystem`：对话节点、选项和条件判断。
- `ClueSystem`：线索发现、查看和状态记录。
- `QuestSystem`：任务目标及完成状态。
- `StoryStateMachine`：剧情标记、事件和结局判定。
- `AudioManager`：环境音、交互音和剧情音效。
- `SaveManager`：本地存档读写。

### 9.4 存储方案

首期采用本地存档，不要求用户账号。

存档内容包括：

- 当前场景和位置。
- 当前剧情节点。
- 已发现线索。
- 已完成谜题。
- NPC 状态。
- 关键选择记录。
- 任务进度。
- 游戏设置。

建议采用版本化存档结构，为后续数据结构升级预留迁移能力。

### 9.5 后端边界

基础游戏流程不依赖后端服务。

如果后续接入 AI NPC、在线存档或其他云端能力，再按实际需求增加 Go 服务或其他后端组件。所有模型 API 密钥必须保存在服务端。

## 10. 美术与 3D 资产规划

### 10.1 美术方向

确定为写实悬疑风，采用第一人称、电影质感的镜头表现。

视觉关键词：

- 深夜环境。
- 低照度与局部光源。
- 冷暖色温对比。
- 老旧建筑和生活痕迹。
- 有限视野与空间纵深。
- 克制的后期效果。
- 环境声音与视觉氛围配合。

### 10.2 资产分类

| 分类 | 资产示例 | 建议制作方式 |
|---|---|---|
| 建筑结构 | 墙、地板、天花板、楼梯 | 模块化制作 |
| 门窗 | 房门、窗框、玻璃 | 复用与简单调整 |
| 家具 | 桌椅、沙发、柜子、床 | 优先寻找合规免费资源 |
| 装饰 | 书籍、花瓶、挂画、摆件 | 资源复用 |
| 灯具 | 吊灯、壁灯、台灯 | 模型与引擎灯光组合 |
| 剧情道具 | 日记、照片、信件、钥匙 | 按剧情需要定制 |
| NPC | 人物模型、基础动画 | 少量重点制作 |

### 10.3 资产制作原则

- 常见家具优先使用现成资源。
- AI 3D 生成额度优先用于关键剧情道具或难以找到的特色资产。
- 优先采用 GLB / glTF 格式。
- 在 Blender 中检查模型比例、材质和碰撞体。
- 通过实例化复用重复物体。
- 控制模型面数、贴图分辨率和材质数量。
- 按区域组织和加载场景资源。
- 检查第三方模型的许可证和商业使用条件。

### 10.4 性能优化

- 对静态场景合理使用烘焙光照。
- 控制实时灯光和动态阴影数量。
- 对重复物体使用实例化。
- 根据距离采用 LOD。
- 优先加载当前区域必需资源。
- 避免无意义的高分辨率贴图。
- 对模型和贴图进行压缩。
- 以目标浏览器的实际帧率和显存占用作为优化依据。

## 11. 非功能需求

### 11.1 运行环境

首期优先支持：

- 桌面端 Chrome。
- 桌面端 Edge。
- macOS 和 Windows 桌面环境。

移动端不作为当前正式版的主要适配目标。

### 11.2 性能要求

- 首屏尽量减少非必要资源。
- 场景资源分批加载。
- 避免长时间卡顿和明显掉帧。
- 对低性能设备提供适当画质选项。
- 对关键交互提供及时反馈。

### 11.3 稳定性

- 游戏刷新或意外关闭后，尽可能恢复最近一次有效存档。
- 存档写入失败时提供明确提示。
- 重要剧情状态变化后及时保存。
- 避免重复触发同一关键剧情事件。

### 11.4 可维护性

- 对话、线索和任务采用数据驱动配置。
- 游戏状态与界面展示分离。
- 核心模块保持清晰边界。
- 为后续新增 NPC、场景和剧本预留扩展空间。

## 12. 正式版快速迭代方式

项目不再采用“四周内完成 MVP”的一次性交付计划，而按可独立验证的迭代单元持续更新。发布节奏、版本号和回滚规则需在正式发布流程中另行确认。

每轮迭代按以下顺序推进：

1. **问题分级：** 先处理崩溃、数据丢失、流程阻塞和核心交互错误，再安排体验、内容与润色。
2. **范围收敛：** 一次迭代围绕一个清晰目标，列出对剧情状态、存档、输入锁定、资源和 UI 的影响。
3. **最小完整实现：** 保持 3D 游戏层、UI 层和内容数据层边界，不借机重写无关模块。
4. **自动化验证：** 运行适用的类型检查、Lint、测试与构建；修复必须补回归测试。
5. **浏览器验证：** 涉及移动、交互、界面、性能或资源加载时，在目标桌面浏览器完成手动走查。
6. **交付记录：** 说明实际验证结果、未验证事项、兼容风险和下一步。

当前迭代工作分为四条并行但有序的主线：

- **内容完成度：** 正式场景、GLB 资产、音频、动画与演出替换临时内容。
- **体验质量：** 输入、镜头、交互反馈、UI 可读性、叙事连续性和性能。
- **稳定性：** 存档兼容、资源释放、错误恢复、浏览器兼容和回归测试。
- **发布工程：** 构建、部署、版本说明、授权记录与回滚能力。

## 13. 当前版本范围与验收标准

### 13.1 当前正式版基线

- 一套完整的首页和游戏入口。
- 一座小型别墅场景。
- 第一人称移动与视角控制。
- 场景碰撞和交互检测。
- 少量具有剧情作用的 NPC。
- 预设对话树和对话分支。
- 线索发现与查看。
- 基础任务和谜题。
- 事件驱动的剧情状态管理。
- 两个主结局与已确认的隐藏结局路由。
- IndexedDB 本地存档。
- 桌面浏览器可运行版本。

### 13.2 验收标准

| 验收项 | 验收要求 |
|---|---|
| 游戏启动 | 能正常进入首页并开始游戏 |
| 场景探索 | 能够在别墅中移动且不会穿越主要障碍 |
| 交互检测 | 能够识别范围内的可交互对象 |
| NPC 互动 | 能够打开对话并选择回应 |
| 对话分支 | 不同选择能够触发不同结果 |
| NPC 状态 | 对话和关键行为能够更新 NPC 状态 |
| 线索系统 | 能够发现、查看并记录线索 |
| 谜题系统 | 能够完成预设谜题并推进剧情 |
| 剧情系统 | 关键事件能够按条件触发 |
| 结局系统 | 能够根据游戏状态进入不同结局 |
| 本地存档 | 刷新或重新进入后能够恢复有效进度 |
| 存档升级 | 旧版本存档能够迁移，损坏数据有明确恢复或重置路径 |
| 输入锁定 | 对话、暂停和其他 UI 模式打开时玩家不会误移动或转动视角 |
| 资源生命周期 | 场景切换、重开和销毁后不遗留重复订阅或常驻资源 |
| 性能 | 在确认的目标设备和浏览器上达到约定帧率与加载时间 |
| 浏览器运行 | 能够在目标桌面浏览器中稳定运行 |

### 13.3 迭代完成定义

迭代完成必须满足《正式版快速迭代规范》的完成定义，包括适用范围匹配的自动化检查、浏览器冒烟、存档迁移、文档同步和风险说明。具体门禁以该规范与后续确认的发布流程为准。

## 14. 风险与应对

| 风险 | 影响 | 应对方式 |
|---|---|---|
| 3D 资产制作耗时 | 高 | 模块化场景、复用免费资源 |
| AI 建模额度不足 | 中 | 只将生成额度用于关键资产 |
| 写实渲染性能压力 | 高 | 烘焙光照、控制阴影和贴图 |
| NPC 制作成本过高 | 高 | 少量重点 NPC，优先基础动画 |
| 剧情分支过多 | 高 | 以已确认故事线为准，新增分支先做依赖与存档影响评估 |
| 对话逻辑难以维护 | 中 | 使用数据驱动对话树 |
| 存档结构变化 | 中 | 使用版本化存档和迁移逻辑 |
| 正式资产替换灰盒 | 高 | 按区域与剧情优先级分批替换，保留可运行回退点 |
| 快速迭代造成回归 | 高 | 固定自动化门禁、目标浏览器冒烟和可回滚发布 |

## 15. 待确认事项

以下内容需要在正式版快速迭代中进一步确认：

1. “正式版”的当前发布状态、对外版本号与发布渠道。
2. 迭代节奏、热修复权限、回滚方式和版本说明规范。
3. 需要兼容的旧存档版本范围与最短兼容周期。
4. 目标浏览器、最低硬件配置、帧率与加载时间预算。
5. 是否启用完整 NPC 配音，以及音频制作和授权方案。
6. 是否扩展章节、区域、NPC 或语言支持，以及相应内容边界。
7. 是否引入 AI 自然语言对话；该能力需单独确认服务、隐私和成本。

## 16. 产品目标总结

《午夜别墅》已进入正式版快速迭代期，目标是持续交付一款能够通过桌面浏览器稳定体验的单人第一人称写实悬疑探索游戏。

玩家进入神秘别墅，通过探索环境、与 NPC 互动、收集线索、解决谜题和作出选择，逐步揭开故事真相，并抵达不同结局。

当前阶段的迭代重点依次为：

1. **可完成：** 保持从开场到多结局的完整流程稳定可玩。
2. **可理解：** 提高交互、线索、任务和剧情的可读性。
3. **可信：** 用正式资产、声音和演出替换临时内容。
4. **可恢复：** 保证存档、错误处理和场景切换可靠。
5. **可发布：** 让每次用户可见改动都能经过验证并安全发布。
6. **可维护：** 在保持模块边界的前提下降低后续内容制作成本。

**最终交付目标：一个拥有完整剧情流程、NPC 互动、线索推理和多结局体验的浏览器端 3D 悬疑游戏。**
